# Reference Test Harness Specification

**Project:** Distributed Intranet
**Document status:** v1.0 — stable. A reference implementation exists (see the repository root); where the two differ, this document is normative and the divergence is recorded in the implementation.
**Depends on:** Core Protocol Spec, Storage & Replication Spec, App Hosting Spec, Real-Time Transport Spec, Search & Indexing Spec (exercises all five, most heavily the first two)
**Consumed by:** implementation/development workflow directly — this is tooling, not a layer other specs build on

---

## 0. Purpose and Scope

This document specifies a CLI-based protocol conformance tool for validating the mechanisms defined across the other five documents — connection establishment, membership/governance, encryption/revocation, storage/replication, and (more lightly) the app-hosting/real-time/search layers — **without building any application on top of the protocol**. It exists specifically so validating this platform never again requires a purpose-built chat app, a friend on a separate physical network, or manual testing as the only option.

It covers:

1. **Design principles** — CLI-only, no app-layer concepts, deterministic and automatable wherever the underlying mechanism allows it.
2. **NAT traversal and connection testing** — a Docker Compose-based simulated-NAT environment, the direct answer to the actual blocking problem from prior work.
3. **Core Protocol conformance tests** — identity, membership/governance, encryption/revocation.
4. **Storage & Replication conformance tests** — chunking, mutable pointers, replica placement, swarm-serving.
5. **Lighter-weight conformance for App Hosting, Real-Time, and Search** — these build on the same underlying primitives already exercised above, so their harness coverage is narrower and more targeted.
6. **A real-world cross-network validation checklist** — a small, manual, pre-release sanity pass, distinct from and supplementary to the automated Docker-based testing that should cover the everyday dev loop.

Out of scope: anything resembling a user-facing application. If a test needs "a chat message" or "a wiki page" as a concept, that's a sign the test belongs in a future application-layer spec's own test suite, not here — this harness only ever speaks in terms of identities, networks, groups, capabilities, published content, and connections.

---

## 1. Design Principles

- **CLI-only, no UI.** Every harness capability is a command-line operation, scriptable and CI-runnable. This was an explicit decision to avoid repeating the earlier mistake of building a full chat app just to have something to test with.
- **No application-layer concepts, anywhere.** The harness's vocabulary is exactly the vocabulary of the five specs: identities, networks, invites, groups, capabilities, mutable pointers, content types, epochs, relays. Nothing about "messages," "channels," "pages," or any other product concept belongs here, even as a test fixture — those inevitably smuggle in product decisions the way the original chat-app-as-test-harness did.
- **Deterministic assertions wherever the protocol itself is deterministic.** Several mechanisms in this design (HRW replica placement, governance log replay, quorum certificate verification) are specified to be deterministic and independently computable — the harness should assert exact-match outcomes for these, not approximate/fuzzy checks, since a mismatch is a real conformance bug, not noise.
- **Multi-node by default.** Nearly every meaningful test requires at least two independent node processes (often more) interacting — the harness should make spinning up N ephemeral, isolated node instances (in-process, containerized, or both) a first-class, low-friction operation.

## 2. NAT Traversal & Connection Testing — Simulated-NAT Environment

### 2.1 Why This Is the Centerpiece

This is the piece that actually blocked prior progress: validating cross-NAT connectivity required a second physical network and another person's cooperation, which made it slow, unrepeatable, and impossible to automate or run in CI. Everything else in this harness is useful; this section is the part that removes a real, previously-blocking obstacle.

### 2.2 Docker Compose Topology

A set of isolated Docker networks reproduces real NAT'd topologies entirely on one machine:

- **`public-net`** — a shared Docker network simulating the open internet. The relay/bootstrap node (Core Protocol Spec §5.2–§5.5) attaches here with a fixed, known address.
- **Per-peer private networks**, each with its own **NAT gateway container** sitting between that private network and `public-net`. A NAT gateway container performs real address/port translation (e.g. `iptables` MASQUERADE rules) and real connection-state tracking — critically, it drops unsolicited inbound connections from `public-net` the way a real NAT does, which is what makes this a genuine simulation rather than just network segmentation with extra steps.
- **A double-NAT chain for at least one peer**, specifically reproducing CGNAT: `client-private → home-router-NAT → CGNAT-layer-NAT → public-net`. This is deliberately the hardest real-world case (the one that caused the most trouble previously) and should always be available as a topology option, not just a single-NAT approximation.

### 2.3 Required Test Scenarios

The harness should be able to stand up and run each of these as a discrete, repeatable, scriptable scenario:

1. **Same-network baseline** — both peers on one private network, no NAT gateway in the path. Validates mDNS discovery and direct connection (Core Protocol Spec §5.1) as the sanity-check floor.
2. **Asymmetric** — one peer behind a single NAT, one directly reachable. Validates the direct-dial and DCUtR tiers independently.
3. **Symmetric-simple** — both peers behind independent single-layer NATs. The expected common case for two different home networks; should validate successful DCUtR hole-punching (tier 2, Core Protocol Spec §5.2).
4. **Asymmetric double-NAT** — one peer behind simple NAT, one behind the simulated CGNAT chain over IPv4 only. Should validate that hole-punching correctly fails where expected, that **the relayed circuit is then closed rather than used**, and that no protocol or application payload crossed it (Core Protocol Spec §5.2). A connection that "works" here is a failure.
5. **Symmetric double-NAT, dual-stack** — both peers behind independent CGNAT-style chains, with globally-routable IPv6 available. The worst realistic case that must still succeed, and it must succeed **over IPv6 at tier 1**, not through a relay: a pair behind CGNAT typically cannot traverse IPv4 at all, and §5.2 makes IPv6 the answer for them. This is the single most important scenario to automate, since it is exactly what was hardest to test manually — and asserting the tier is what stops it passing for the wrong reason.
6. **Symmetric double-NAT, IPv4 only** — the same pair with no IPv6 path. **Expected outcome: no connection.** §5.2 states this plainly rather than reaching for a relay, and the harness asserts the absence: both peers stay reachable to any third member either can reach, and neither sends payload over a circuit.

### 2.4 Assertions Are Tier-Specific, Not Just "Did It Connect"

A passing test must confirm **which tier** a connection succeeded through, not merely that a connection eventually happened — a bug that silently forces every connection through a relay is functionally "working" and defeats the entire point, so it must fail the suite rather than pass it. This means asserting on the connection-lifecycle events implied by Core Protocol Spec §5.2 (direct connection established / DCUtR upgrade succeeded / DCUtR upgrade failed / circuit closed), and each scenario in §2.3 has an expected outcome the harness checks against.

**The strongest assertion here is a negative one: no payload crossed a circuit.** Since §5.2 permits a relayed circuit to carry only the DCUtR negotiation, a relay's byte counter is a direct test of conformance — a conformant pair leaves it at the negotiation's own cost and no more. A harness that only checks whether peers connected cannot see the failure this rule exists to prevent, because that failure looks exactly like success.

### 2.5 Relay Resource Limit & Rate-Limit Verification

Given the real gap found in prior relay code (a rate limiter that computed a decision but never enforced it, and was keyed by a trivially-regenerable libp2p peer ID rather than authenticated identity — Core Protocol Spec §5.3), this is an explicit, named test case, not an incidental one: the harness should be able to spin up many synthetic per-network identities issuing rapid reservation requests against a relay under test, and assert that **the configured limits are actually enforced** — connections beyond the limit are genuinely rejected, not merely logged.

**The identity-keyed half of this test belongs against a member relay, not a stateless bootstrap relay — a scoping this document previously got wrong by inheriting §5.3's original, over-broad phrasing.** Asserting that "identity, not peer ID, is what's being rate-limited" presumes the node under test can tell a real identity from a freshly generated keypair, which requires governance state that a bootstrap relay deliberately does not hold (Core Protocol Spec §5.3.1, §5.4). Against a bootstrap relay the assertion is unsatisfiable by any conformant implementation, so the test must not make it: what to assert there is that the **global ceilings** bind — total reservations, concurrent circuits, circuit duration, bytes per circuit — which is exactly the defect class this test exists to catch, and which needs no state at all. Against a **member** node offering `relay_bootstrap_willing`, the full assertion stands, including that regenerating a peer ID without a legitimate new per-network identity does not bypass the limit, and that pre-admission activity under a multi-use or bearer invite is metered per-invite rather than per freely-mintable identity.

## 3. Core Protocol Conformance Tests

- **Identity & multi-device linking (§1):** derive per-network identities from a master seed and confirm unlinkability (two per-network public keys reveal no correlation without voluntary disclosure); issue and revoke device certificates and confirm a revoked device's signatures are rejected without requiring master-seed rotation.
- **Membership & governance (§2):** create groups, grant/revoke capabilities, confirm the `everyone` governance-tier denylist is actually enforced as a *class* rather than a fixed list — specifically test that a capability defined and tagged governance-tier *after* the base spec (simulating a consuming spec's future addition) is still correctly rejected if granted to `everyone`, not just the originally-enumerated ones; confirm `manage-membership:<group>` is correctly blocked from `everyone` exactly when the target group holds governance-tier power, and correctly allowed when it doesn't; test both membership-revocation cascade modes (default non-cascading, opt-in cascading with a time window) and confirm the correct set of memberships survives or is removed in each case; run the same governance log independently on multiple nodes and assert they replay to an identical computed state — this is a deterministic check and should be a hard pass/fail, not approximate.
- **Governance log fork creation, bounded finality, and reconciliation:** deliberately partition a set of harness nodes (drop gossip connectivity between two groups), have each side independently append conflicting entries referencing the same parent, then heal the partition and confirm every node converges on the identical canonical branch per the fork-choice rule (Core Protocol Spec §2.7.1) — assert the deterministic sibling tie-break for single-entry forks and longest-branch reconciliation (by capability-gated action count only) for deeper ones. **As a specific negative test for the branch-grinding exploit a second review pass identified:** have the losing side pad its branch with many capability-free device-certificate entries and confirm this does *not* let it win against a shorter branch with more capability-gated actions. Confirm entries unique to the losing branch are treated as voided, that the mandatory voided-actions report correctly lists them (including a specific test where a revocation was on the losing branch, confirming the report flags it for resubmission), and that a branch which has crossed the bounded-finality threshold can no longer be displaced by a later, longer competing branch presented after the fact. **The threshold is now concrete and the test asserts against it directly (Core Protocol Spec §2.7.1): k = 10 capability-gated governance actions *and* T = 30 minutes, both required.** Because both conditions are conjunctive, this needs three distinct cases, not one: (a) a branch that is 10+ capability-gated actions deep but **younger** than 30 minutes must still be displaceable by a longer competing branch; (b) a branch older than 30 minutes but **shallower** than 10 capability-gated actions must likewise still be displaceable; (c) only a branch satisfying both must be immune. Case (a) is the anti-grinding regression test specifically — an attacker able to emit capability-gated actions rapidly must not be able to buy finality with speed alone. The harness should drive T using an injectable/virtual clock rather than real 30-minute waits, so this stays CI-runnable; the age comparison is what's under test, not the wall-clock duration.
- **Partition-with-competing-rotations round trip:** the specific, compounding case a second review pass flagged as needing its own dedicated test — partition the network such that both sides independently trigger an epoch rotation (each side revoking a different, or even the same, member), let members on each side tentatively apply their side's rotation and begin using it, then heal the partition. **With k and T now concrete (Core Protocol Spec §2.7.1), this test can specify its timings exactly rather than gesturing at them:** the partition must be healed while both branches are still short of finality — fewer than 10 capability-gated actions deep on each side, or less than 30 minutes old on the virtual clock — since a rotation that has already finalized is by definition no longer voidable and would exercise nothing. Run the complementary case too: hold the partition past **both** thresholds on one side, heal, and confirm the finalized side is *not* displaced even if the other side presents more capability-gated actions afterward, and that members on the finalized side have correctly discarded their superseded MLS secrets by then (§3.3's retention window having closed) rather than retaining them indefinitely. Confirm: (a) every node converges on one canonical rotation per the fork-choice rule, (b) members who tentatively applied the now-voided rotation successfully re-welcome onto the canonical one using their retained prior-epoch MLS state (Core Protocol Spec §3.3), without needing to leave and rejoin the network, and (c) content on both sides remains accessible post-heal to legitimately remaining members, with any DEK wrappings referencing the voided rotation's hash correctly detected as stale and opportunistically re-wrapped against the canonical rotation (Storage Spec §5.3.1).
- **Vote-based admission and clock-skew at the close boundary (§2.6.1):** simulate a frozen-electorate vote, gossip ballots across multiple node instances with deliberately skewed local clocks near the close time, and confirm every node's outcome is governed by quorum certificate existence rather than diverging based on which ballots each node happened to have collected locally. Specifically test the corrected certificate-validity definition: a certificate assembled *after* close time, but referencing only ballots whose own signed timestamps are at or before close, must still be accepted as valid — this is a regression test for the assembly-time-vs-ballot-timestamp ambiguity a second review pass caught. Also include a case where no valid certificate is ever produced, confirming the vote is treated as failed by every node, with no deadline pressure on certificate assembly itself.
- **Group encryption & revocation — corrected to match the honest guarantee (§3):** join a network, confirm epoch key receipt; revoke a member and confirm (a) the epoch actually advances via a cheap DEK re-wrap (not full content re-encryption — assert CIDs of existing content are unchanged after rotation), (b) the revoked identity **cannot** obtain any object's DEK wrapped for the first time after revocation, (c) the revoked identity **cannot** obtain new ciphertext bytes for content published or edited after their revocation, once honest nodes' governance-log replay has converged on the revocation (Storage Spec §5.4 — assert eventual convergence, not instantaneous blocking, consistent with the corrected propagation-window framing), and (d) — the corrected, no-longer-overstated part — the revoked identity **can** still decrypt whatever content and key material it had already legitimately obtained before revocation, confirming the harness itself doesn't assert the impossible stronger guarantee this document used to claim. Remaining members retain full access via the new epoch key throughout. This is the harness's most important correctness test, since it's the actual, honest revocation guarantee the whole encryption design exists to provide.
- **Invites & admission modes (§5.4, §5.6–§5.7):** issue and consume invites under both auto-admit and explicit-intake policy, confirm a waiting-room node under explicit intake genuinely holds zero capabilities and no epoch key until manually admitted, and confirm the invite payload itself never needs to carry more than connection-bootstrap data (§5.7) — i.e., a node should be able to reach full participation using only what the invite provided plus ordinary post-connection sync, never anything smuggled into the invite payload beyond spec. Additionally, confirm relay/bootstrap rate limiting for pre-admission (waiting-room) identities is correctly scoped per-invite, not solely per-identity — spin up many synthetic waiting-room identities off one multi-use invite and confirm the limit catches the pattern rather than treating each freely-minted identity as independently costly.

## 4. Storage & Replication Conformance Tests

- **Content-defined chunking and determinism (§1):** publish content, make a small edit, re-publish, and confirm only the chunk(s) actually touched by the edit produce new CIDs — this is a direct, automatable check of the delta-fetch property the whole chunking design exists to provide. Additionally, encrypt the same chunk plaintext under the same object DEK twice, independently, and confirm the resulting ciphertext is byte-identical both times — a direct regression test for the deterministic-encryption requirement (§1.2), since a correctness bug here would silently break delta-fetch and deduplication without any obvious symptom short of this specific check.
- **Mutable pointers and concurrent updates (§2):** publish, update, and confirm version-ordering rejects stale/replayed pointer states; confirm the two-gate publish check (content-type allowlist + `publish:<content_type>` capability, Core Protocol Spec §2.8) is actually enforced — a publish attempt failing either gate must be rejected, and a network without `app-bundle` on its allowlist should be confirmed to have no path to publish one under any capability configuration. Additionally, simulate two nodes concurrently publishing competing updates to the same pointer (both building on the same prior version, so both records claim the **identical** version number) and confirm the collision is resolved by the deterministic tie-break now specified in Storage Spec §2.2 — **lower record-hash wins**, the same rule as governance log siblings (Core Protocol Spec §2.7.1, point 1). This is a deterministic, exact-match assertion, not an approximate one: every node presented with both records must independently select the same winner, in either arrival order, so run the case with the records delivered in both orders and confirm the outcome is identical. Confirm the losing record is cleanly rejected and retryable at an incremented version against the now-canonical record, rather than silently corrupting pointer state or being merged. Confirm the harness asserts **only** the tie-break — it must not assert any content-merge behavior, which Storage Spec §2.2/§7 deliberately leaves to the application layer.
- **DEK commitment/wrapping split and re-wrap authorization — a direct regression test for the signature contradiction a second review pass found:** confirm a `MutablePointer`'s signed fields never include the current DEK wrapping (only `dek_commitment`); publish an object as owner A, then have a *different* node (not the owner) produce and publish a `DekWrapping` for it following a rotation, and confirm honest nodes accept it as valid — verified against `dek_commitment`, not against a signature from `owner_identity`. Confirm a wrapping that doesn't hash-match the pointer's `dek_commitment` is rejected regardless of whose signature is on it. Confirm a `DekWrapping` publish never increments the pointer's `version` counter.
- **Distributed Append-Sets and posting validation (§2.5, Search Spec §3.1):** publish multiple independent entries to the same collection from different identities and confirm the collection is genuinely enumerable (not just individually look-up-able) by any node — but also confirm the harness doesn't assume completeness (§2.5's best-effort caveat): construct a collection large enough to exceed a typical provider-record response cap and confirm consuming logic (e.g. search ranking) degrades gracefully rather than assuming it saw everything. As a negative test, publish a syntactically valid but improperly-signed, non-current-member-signed, or delisted-content-referencing entry and confirm honest nodes reject/ignore each case — for the third, produce the delisting as an actual `ModerationEntry` appended to the governance log by a `moderate-content` holder (Core Protocol Spec §2.7) and confirm honest nodes derive the delisted state by replay, not from any side channel; also confirm an entry signed by an identity *without* `moderate-content` is rejected as an invalid `ModerationEntry` and therefore does **not** delist anything, and that a subsequent `relist` restores the entry's validity — this directly exercises the full three-part posting-validation requirement (Storage Spec §2.5, Search Spec §6.1), which two successive review passes incrementally closed.
- **Replica placement (§3.3):** given a fixed CID and a fixed capability ledger snapshot, confirm multiple independent nodes compute the identical HRW-ranked replica set from `score = hash(CID, node_id) × storage_offered` — another deterministic, hard pass/fail check. **Add a direct regression test for the contradiction a review pass found here:** give several nodes *deliberately divergent* local `reliability_signal` observations about the same peers, then confirm they still compute a byte-identical replica set — proving the placement function reads only gossiped `storage_offered` and takes no local-only input (Core Protocol Spec §4.6). A build that lets reliability influence placement would pass a naive same-observations test and fail only this one, which is precisely why it needs to exist. Assert the same property for live-stream first-tier assignment (Real-Time Spec §3.3), which reuses the same HRW computation weighted by `bandwidth_cap` instead of `storage_offered` — confirm both that its tier is identical across nodes with divergent local observations, and that the two call sites genuinely share one parameterized ranking routine rather than having drifted into two implementations. Separately, confirm the intended remediation path still works: fail a selected replica holder and confirm the repair loop (§3.4) re-places its content onto the next nodes in the same deterministic ranking, since repair — not placement weighting — is now where unreliable nodes are corrected for.
- **Swarm-serving and `read-content`-gated access (§4):** fetch content from multiple simultaneous sources, confirm rarest-first prioritization is actually followed under a scarce-chunk scenario, and confirm a corrupted/malicious chunk from one source is detected and correctly re-requested from another rather than silently accepted. Additionally, confirm an honest serving node refuses to serve content bytes to a requester who does not hold `read-content` (Core Protocol Spec §2.2) — including the specific case of a waiting-room identity under explicit intake, which is a *valid, non-revoked* identity but correctly still refused, a distinction a second review pass identified as under-specified in an earlier version of this gate. This deserves its own explicit, isolated test rather than only being exercised as a side effect of the revocation test in §3.
- **Rotation cost — churn simulation (§5):** simulate a network with realistic membership churn (a steady rate of joins/revocations over simulated time) and measure actual rotation cost per event — assert it scales with the number of *live objects requiring re-wrap*, not with total content volume, as a concrete, measurable confirmation that the envelope-encryption rework (§5.2) delivers the cheap-rotation property it claims, rather than only asserting this architecturally. Confirm the re-wrap can be performed by any current member's node, not only an object's original owner (using the commitment/wrapping split, not a contradictory owner-signature requirement), and that no owner-offline blackout window occurs at any point during the simulation.

## 5. Lighter-Weight Conformance: App Hosting, Real-Time, Search

These build on primitives already exercised above, so harness coverage here is narrower — targeted at the parts genuinely specific to each document, not re-testing the underlying storage/governance mechanics:

- **App Hosting:** sandbox isolation boundary (an app-bundle cannot access another app's storage or the visiting user's keys); publishing-policy enforcement (`open` vs. `reviewed`, and that review is required per-version, not just on first publish); name registry governance-log anchoring (App Hosting Spec §4.3) — as negative tests, attempt to register a name with a backdated timestamp and confirm it doesn't gain priority (since ordering is governance-log-derived, not self-attested-timestamp-derived), and confirm a legitimate registration does *not* lapse or become hijackable even if its append-set discovery entry goes unrefreshed past its TTL — this is the direct regression test for both vulnerabilities a second review pass identified in the original append-set-only design. Separately, confirm `register-app-name` (claiming an unclaimed name) and `reclaim-app-name` (reassigning a claimed one) are correctly enforced as distinct, separately-gated capabilities — a broad grant of the former must not permit hijacking an already-claimed name.
- **Real-Time Transport:** mesh↔relay threshold transition triggers at the configured participant count; relay failover completes without dropping the session (can be tested without real audio/video — the transport/signaling layer is what's under test, not media quality).
- **Search & Indexing:** a publish produces the expected default-metadata postings automatically with no separate indexing step; an opted-in `IndexDocument`'s fields are correctly searchable; a query never returns results from a different network under any circumstance (this is a hard invariant worth its own explicit negative test, given how central network isolation is to this whole design). As a negative test specific to a gap a second review pass identified: delist a piece of content whose publisher remains a current member — via a `ModerationEntry` in the governance log (Core Protocol Spec §2.7), the concrete mechanism behind this check — and confirm its postings are correctly excluded from search results going forward, even though the publisher's own signature and membership status both remain valid. Confirm the exclusion holds while the publisher keeps re-announcing the posting (delisting must not be outlastable by continued refresh, since it lives in the log rather than the append-set), and that a `relist` restores the content to results without requiring re-publication — this isolates the third validation check (referenced-content moderation state) from the other two.

## 6. Real-World Cross-Network Validation Checklist

The Docker-based environment (§2) should cover the everyday development loop and CI. It cannot fully replace real-world validation against actual, unpredictable consumer NAT/CGNAT implementations in the wild — those vary in ways a simulation can approximate but not guarantee to match exactly. A small, explicit, manual checklist — run before a release rather than on every change — should confirm: a real connection across two genuinely different consumer ISPs succeeds; a connection from a mobile carrier network (a common real-world CGNAT case) succeeds; and a relay deployed on the intended hosting platform is reachable and correctly verifiable end-to-end. This is intentionally small and infrequent — the goal is catching anything the simulation couldn't capture, not replacing the automated suite.

## 7. Summary: What This Tool Is For

- A CLI tool, never a UI, speaking only in the vocabulary of the five specs — no application concepts, ever.
- Its centerpiece is a Docker Compose NAT-simulation environment (§2) covering same-network, asymmetric, symmetric-simple, and both single- and double-NAT (CGNAT) scenarios, with assertions on *which connection tier succeeded*, not just whether a connection eventually happened.
- It includes a named, explicit test for the exact class of bug found in prior relay code — a rate limiter that doesn't actually enforce, or is keyed by regenerable peer ID rather than authenticated identity.
- Deterministic protocol mechanisms (governance log replay and bounded-finality fork-choice reconciliation, quorum-certificate outcomes measured by ballot timestamp rather than assembly time, HRW placement, same-version mutable-pointer tie-break, chunk and DEK-wrap encryption) get exact-match assertions, not approximate checks. Two of these carry an explicit *negative* determinism assertion as well: HRW placement must produce identical results across nodes holding **divergent local `reliability_signal` observations** (§4), proving no local-only state leaks into a cross-node computation, and bounded finality must require **both** k = 10 capability-gated actions and T = 30 minutes rather than either alone (§3).
- The most important single correctness test in the whole harness is the revocation round trip (§3): revoke a member, confirm they provably lose access to anything new — key material and content bytes alike — while confirming everyone else retains full access, and confirming the harness itself asserts the honest, achievable guarantee rather than the impossible one this project's own documents briefly and mistakenly claimed before a review pass caught it.
- A dedicated churn-simulation test (§4) confirms rotation cost scales with live-object count, not total content volume — a concrete, measured check that the envelope-encryption rework actually delivers cheap rotation, not just an architectural claim.
- A dedicated partition-with-competing-rotations test (§3) confirms the harder, compounding case a second review pass specifically identified: that fork reconciliation, MLS state re-welcome, and stale-wrapping cleanup all work together correctly when a fork happens to straddle an epoch rotation, not just when forks and rotations are tested in isolation from each other.
- The name-registry tests (§5) specifically confirm two attacks a second review pass identified in an earlier, append-set-only registry design — timestamp backdating and TTL-lapse hijacking — are now structurally prevented by governance-log anchoring, not merely discouraged.
- Real-world manual validation (§6) is a small, infrequent supplement to the automated suite, not a replacement for it.

## 8. Explicitly Open Questions

All three questions previously listed here were implementation tasks awaiting real data, and the reference implementation has now produced it. They are recorded as resolved rather than deleted, because two of the answers are counter-intuitive enough to be worth stating.

1. ~~Exact `iptables`/NAT-gateway configuration per NAT type.~~ **Resolved.** The configuration is in the reference harness. One finding is worth promoting out of it, because getting it wrong produces a NAT that looks correct and silently defeats tier 2: **a gateway must `DROP` unsolicited inbound packets, never reject them.** Only `FORWARD` is obvious; a hole-punch SYN is addressed to the gateway's *own* address, so it is routed to `INPUT`, and an `INPUT` chain left at the default `ACCEPT` answers with an RST. Hole-punching depends on that first SYN being *lost*: the initiator dials first, its SYN reaches a NAT whose peer has not yet dialled out, and a real NAT discards it so that the retransmit — by which time the peer has dialled and the mapping exists — gets through. An RST removes the retransmit and the dial fails permanently on the first packet. An emulated NAT that rejects rather than drops is not a stricter NAT, it is a broken one.
2. ~~In-process versus containerized node instances.~~ **Resolved: both, split by what is under test.** Containerized for anything where the network path is the subject — the NAT scenario matrix (§2.3). In-process for protocol conformance, which is the large majority: propagation, partition and heal, fork choice, chunk transfer, discovery, call media. The split is not a performance compromise. §3 already requires a virtual clock for the bounded-finality thresholds rather than real 30-minute waits, and a partition is modelled by not connecting two nodes — so most protocol properties are *better* tested in-process, where they are deterministic and CI-runnable, and containers add realism only where the realism is the point.
3. ~~CI runtime budget for the full matrix.~~ **Resolved by measurement.** The in-process suite runs in roughly two minutes and is appropriate on every commit. The Docker NAT matrix is minutes longer and needs a Docker host, so it belongs on a slower cadence — per pull request or nightly — rather than per commit. The split in question 2 is what makes this affordable: it keeps the per-commit gate broad and fast, rather than forcing a choice between slow feedback and thin coverage.
**Previously open, now resolved:** concrete values for the governance log's bounded-finality reorg depth and age threshold, which mirrored Core Protocol Spec §7's open item. These are now **k = 10 capability-gated governance actions and T = 30 minutes, both required** (Core Protocol Spec §2.7.1), so the fork-choice and partition-with-competing-rotations tests (§3) specify concrete entry counts and waiting periods directly. They remain tunable starting defaults — this harness is expected to be the source of the propagation and partition-duration data that eventually revises them, which is an argument for reporting observed values from these runs, not only pass/fail.
